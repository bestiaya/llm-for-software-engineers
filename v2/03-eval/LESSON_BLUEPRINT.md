# 第03章教学蓝图

面向会编程、尚未系统学过机器学习的软件工程师。读完能用一份事先固定的标准逐题评价一个应用，检验评分程序本身，分清评分与运行时检查，并说清十条题的结果能支持什么结论、不能支持什么结论。

## 阅读顺序

1. 从“新版更好吗”这个问题开始。先固定标准：第 02 章的十条期望行为，两版应用都用它评。说明旧版的输出怎样判分，在看结果之前声明。
2. 逐题看新版应用：模型原文、应用行为、与期望的逐项对照。评分骨架只有几行，正文直接展示。
3. 检验评分程序：四组人工构造的错误输出各自应该被抓到哪几题。第四组的拒绝原因不对，用来说明期望行为写得不细时评分会放过什么。它们不是模型的回答，不计入真实模型的统计。由“全部拒绝也能通过四题”引出总分要和逐题结果一起看。
4. 用同一份标准比较两版应用，看通过数和逐题变化。结论的写法是“应用对这份约定的满足程度变了”，不写成模型能力提高。
5. 分清评分程序和运行时检查：前者手里有标准答案，只在已知的题上起作用；后者没有标准答案，每次请求都执行。
6. 说明这十条题的用途和结论范围。阶段检查：给一条没见过的输入写期望行为，并指出哪些能由程序检查。检查题的答案必须能从前面的约定推出来；约定没有写到的说法只作讨论题。

## 核对依据

正文里的通过数、逐题结果和模型原文，以 `records/v1/`、`records/v2/` 的真实记录和 `lab.py` 的输出为准；采集方式见 `records/README.md`。人工构造的错误输出在 `inputs/synthetic-outputs.json`，正文和输出都要标明它们的来源。

评分程序检查的是应用的判定，包括是否组装天气查询、由谁因为什么原因拒绝，不只看模型回答的文本。查询的城市和天数取自组装好的查询，是否说明默认天数取自对用户说的话。实验不发送天气查询。

十条题参与过约定的修改，属于开发与回归题。正文不据此估计应用在其他说法上的可靠性，也不据此评价模型的能力。
