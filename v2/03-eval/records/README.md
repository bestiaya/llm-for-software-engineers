# 十条输入在两版约定下的真实模型回答

本目录保存 20 份记录。`v1/` 用的是第 01 章的两字段约定，`v2/` 用的是第 02 章三种结果的约定。每个子目录十份，文件名是输入的编号，从 `w01.json` 到 `w10.json`。十条输入的原话和期望行为见[第 02 章的输入文件](../../02-contract/inputs/cases.json)。

## 怎样采集的

2026-11-23，[采集程序](../capture.py)通过 Codex CLI 0.166.0 请求 `gpt-6.1-sol`，推理档位设为 `medium`。每条输入在每版约定下保存一份完整的回答。

- 交给命令行的全部文字是“约定的指令、空行、用户原话”，保存在 `capture.stdin`。两版的指令分别来自[第 01 章的请求文件](../../01-request/inputs/weather-request.json)和[第 02 章的约定文件](../../02-contract/inputs/contract-v2.json)。
- `response.text` 是模型交回的原文，与 `cli_message_event` 里的正文一致。
- 每次调用都从一个空的临时目录启动，保存的调用记录里没有助手消息以外的条目。命令行的只读模式并不限制读取别处的文件，所以这里不能说模型一定看不到课程仓库。
- 没有服务端独立回报的模型标识，`model_reported` 记为 `unknown`。命令行自带的指令和底层的网络报文不在记录里。

## 采集过程中发生了什么

采集当天访问模型服务的网络不稳定。命令行启动时刷新模型列表的请求多次超时，单次调用从二十多秒到几分钟不等。

- 最初把单次调用的上限设为 240 秒，有 13 次调用在上限内没有返回。这些调用没有产生任何回答，也没有留下记录。
- 随后把上限放宽到 600 秒，缺的记录全部补齐。
- 每份记录保存的都是那条输入在那版约定下**第一次完整返回的回答**，没有按内容挑选。唯一的例外是 `v1/w05`：排查超时原因时单独调用过一次，那次的回答是 `{"city":"杭州","days":2}`，没有保存；随后采集程序取得并保存的回答与它相同。
- 新约定的指令在采集之前写定，采集之后没有改过。

## 这些记录能说明什么

- 它们是第 03 章评测的原始材料，用途是演示、开发和回归。实验只用它们重走应用的判定，不发送天气查询。
- 每条输入每版约定只保存了一份回答，采集期间还发生过超时后的重新调用和一次没有保存的诊断调用。现有材料不能用来估计重复调用时回答会不会变。
- `response.usage` 是命令行回报的用量，包含命令行自带的上下文，不能直接当作模型接口的计费样本。
- 同一条输入在两个子目录里的差别，来自交给模型的指令不同。请求的模型和档位相同，采集在同一天完成。

## 想自己重新采集

需要本机装有 Codex CLI 并已登录。已有的记录不会被覆盖，所以要先指定另一个输出目录：

```bash
python3 v2/03-eval/capture.py --out my-records
```

回放自己采集的记录不在本章的必做范围内。指令如果改过，旧记录就不再与它配套，实验会拒绝回放。
